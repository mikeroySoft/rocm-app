Product scope

Runtime lifecycle, without system-level ambiguity.

The product vocabulary is deliberately closed. ROCm App can inspect the machine and manage side-by-side ROCm runtimes. Drivers stay read-only, unsupported hosts receive no actions, and GPU-required work never falls back silently to the CPU.

01 / INSPECT

Understand the machine

Read platform support, GPU identity, components, managed runtimes, driver inventory, update trust, and a health verdict from one versioned snapshot.

02 / INSTALL

Install side by side

Resolve a concrete release or nightly version for a validated GPU family, show the plan, then install a managed wheel runtime without replacing the system driver.

03 / UPDATE

Update by runtime key

Target an exact managed runtime. The controller resolves “latest” before review so approval always names the version that will land.

04 / ACTIVATE

Change the active ROCm

Validate and activate an installed runtime by its side-by-side key. The previous working runtime remains represented in the machine snapshot.

05 / VALIDATE

Diagnose before guessing

Validate a selected runtime and surface explicit health reasons such as absent GPU, failed validation, stale update data, or an incomplete probe.

06 / REMOVE

Remove managed runtimes

Uninstall only an explicitly selected managed runtime. No request variant can represent a driver install, update, or removal.

Repository status, not a launch claim. The versioned contract, Rust controller, production adapters, and typed Tauri commands are implemented. The React renderer still reads deterministic fixture snapshots; wiring it to controller_snapshot and building review/progress screens remain integration work.

Architecture, progressively disclosed

Start with the boundary. End at the approval protocol.

Four views move from product context to module-level seams. The interactive runtime view is grounded in the current controller API: snapshot, plan, and execute.

Level 01 · Product context

One desktop surface, three hard boundaries.

The app sits between the developer and managed ROCm. It delegates mechanics to the bundled CLI, treats drivers as inventory, and never offers mutation on unsupported hosts.

Level 02 · Runtime containers

Rules move down; typed state moves back up.

Presentation stays replaceable because every product decision lives in rocm-app-core. Tauri is a composition root, not a second domain layer.

Level 03 · Interactive runtime protocol

Walk the handoffs, one payload at a time.

Choose a user goal, switch the host mode, then step through the exact trust boundary. Nodes are draggable; selecting one jumps to its first appearance in the active flow.

Implementation boundary: the Rust controller, onboarding policy, adapters, bundled-CLI calls, and Tauri commands shown here exist. React still renders fixture snapshots; its controller/onboarding client is the proposed integration.

The source tree mirrors the trust boundary.

Non-negotiable boundaries

            
The product is defined as much by what it refuses.

          

          

            These constraints are architecture, not disclaimer copy. They keep the desktop app
            narrow enough to reason about and safe enough to put in front of system-changing
            operations.
          

        

        

          

            
Supported and explicit

            
    
              
  • 
                Native Windows 11 x86_64 and native Linux x86_64.
              
    • 
              
  • 
                Managed ROCm runtimes installed side by side and addressed by exact runtime
                  keys.
              
    • 
              
  • 
                An explicit review for every runtime mutation; plans expire and cannot be
                  replayed.
              
    • 
              
  • 
                Installing the app bundles a compatible CLI. Installing the CLI alone does not
                  install the app.

Out of scope by design

            
    
              
  • 
                Driver installation, update, or removal. The app reports version and official
                  support links only.
              
    • 
              
  • 
                WSL, macOS, ARM hosts, and AMD Instinct hardware.
              
    • 
              
  • 
                Silent CPU fallback for GPU-required work.
              
    • 
              
  • 
                Arbitrary process execution from the webview, PATH-selected CLI binaries, or
                  shell interpolation.
